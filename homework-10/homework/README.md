# ДЗ 10.1. Префиксные суммы и бенчмарки

## Запуск

Использован выданный отдельный модуль `bootcamp/session3`, Go 1.22 или новее.

Из корня репозитория:

```bash
cd homework-10/homework
go test ./...
go vet ./...
go test -run '^$' -bench SumRange -benchmem -count=3 ./...
```

Для второго размера нужно заменить только `benchN` в `bench_test.go` с `100_000` на `1_000_000` и повторить команды. `benchQ = 1_000` в обоих случаях. В сдаваемом файле установлено `benchN = 100_000`.

## Как устроено решение

`NumArray` хранит поле `prefix` длиной на один элемент больше исходного массива. `prefix[i]` равен сумме первых `i` элементов, а `prefix[0] = 0`.

В `Constructor` один раз вычисляю `prefix[i+1] = prefix[i] + nums[i]`.

Для включённых границ запроса `[left, right]` ответ равен `prefix[right+1] - prefix[left]`. Из суммы от начала до правой границы убирается сумма элементов перед левой.

Для `[-2, 0, 3, -5, 2, -1]` префиксы равны `[0, -2, -2, 1, -4, -2, -3]`. Запрос `[2, 5]` возвращает `-3 - (-2) = -1`.

Исходные значения копируются в накопленные суммы. Изменение переданного среза после построения не меняет результаты запросов.

## 1. Сложность

Пусть `n` — длина исходного массива, `q` — число запросов, `L = right - left + 1` — длина одного запрошенного отрезка.

| Операция | Время | Дополнительная память |
|---|---|---|
| `SumRangeNaive`, один запрос | `O(L)`, в худшем случае `O(n)` | `O(1)` |
| `Constructor` | `O(n)` | `O(n)` для `prefix` |
| `SumRange`, один запрос | `O(1)` | `O(1)` поверх уже построенного объекта |
| Наивный прогон `q` запросов | В худшем случае `O(q × n)` | `O(1)` поверх подготовленных данных |
| Префиксный прогон с построением | `O(n + q)` | `O(n)` |

Наивный метод каждый раз проходит по всему запрошенному отрезку. Префиксный метод один раз просматривает массив, затем отвечает на запрос двумя обращениями к срезу и вычитанием.

## 2. Что измеряется

Данные и 1000 запросов готовятся до `b.ResetTimer()`. Для каждого варианта используется одинаковый генератор `rand.New(rand.NewSource(1))`.

В каждой итерации `b.N`:

- наивный вариант выполняет все 1000 запросов;
- префиксный вариант строит новый `NumArray` и выполняет все 1000 запросов.

`ns/op` показывает время всего этого прогона, включая построение префиксов во втором варианте.

Результаты запросов складываются в контрольную сумму, которая сохраняется в `benchmarkTotal`. Это сделано одинаково для обоих вариантов, чтобы вычисленные ответы использовались и компилятор не мог удалить их как ненужные.

Тело готовой `SumRangeNaive` сохранено. Готовые проверки находятся в `prefix_test.go`. Дополнительно локально проверены повторные запросы к одному объекту, нули, отрицательные числа, один элемент, сохранность построенных данных и совпадение обоих методов на запросах с тем же генератором и начальным состоянием для двух размеров входа.

## 4. Выводы

По медианам при `n = 100 000` префиксный вариант быстрее примерно в 50,7 раза. При `n = 1 000 000` — примерно в 75,3 раза.

В этих замерах увеличение входа в десять раз увеличило время наивного варианта примерно в 12,2 раза, а префиксного — в 8,2 раза. На точные отношения влияют работа памяти, кэш процессора, выделения и сборка мусора.

Причина преимущества префиксов в том, что длинные отрезки не просматриваются заново для каждого из 1000 запросов. Вместо повторных обходов выполняется одно построение за `O(n)` и 1000 операций за `O(1)`.

При фиксированном числе запросов обе оценки линейны по `n`, но у наивного варианта коэффициент связан с числом и длинами запросов. По нескольким замерам нельзя доказывать класс сложности — его объясняет алгоритм.

Префиксный вариант расходует дополнительную память линейно от размера входа. Выгода особенно заметна при большом числе запросов к неизменяемому массиву.

## 5. Особые случаи и контракт

- `left = 0` работает через нулевой `prefix[0]`.
- `left = right` возвращает один элемент.
- Запрос на весь массив использует последний префикс.
- Нули и отрицательные значения обрабатываются обычным сложением и вычитанием.
- Несколько запросов используют один уже построенный объект.

По условию массив непустой, а индексы удовлетворяют `0 <= left <= right < len(nums)`. Проверки входов за пределами этого контракта не добавлены.
